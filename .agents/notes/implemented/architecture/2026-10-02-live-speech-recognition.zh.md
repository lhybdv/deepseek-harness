# Agent Note：用户仍在说话时进行实时语音识别

Status: implemented

[English](2026-10-02-live-speech-recognition.md) | 中文

## Problem

此前的语音输入只识别一段完整录音。浏览器用 `MediaRecorder` 采集整段语音，重采样为规范 16 kHz WAV，等用户停止后再发送；Host 收到后才开启识别会话并按真实时间重放音频。因此一个十秒的问题会有十秒不显示任何内容，而这段等待的后半段仅仅来自按语速重放一个已存文件。云端识别器在听到句子的同时就会报告（其中间句还会被就地修正），但这些报告无处可去：接缝只提供 `transcribe(input) → Promise<Transcript>`，Remote 只有一个一元调用，输入框也只有一种「识别中」状态。

## Decision

接缝在完整录音操作之外增加一个可选的实时操作。`SpeechProvider.transcribeStream(input, signal)` 消费 `SpeechStreamInput.chunks` 并产出 `SpeechSegment`；每份报告重述完整转写，最后一份为最终结果。`SpeechProviderInfo.streaming` 说明提供方是否实现该操作，调用方据此在开始采集前选择路径。`speechToText.resolveStream()`/`stream()` 对应 `resolve()`/`transcribe()`：同样的注册归属、同样的显式 Provider 绑定、同样拒绝回退；撤销注册会像中止完整录音任务一样中止并等待实时会话。未实现该操作的提供方会让 `stream()` 失败，而不会静默地改为识别完整录音。

Remote 把实时录音承载在一条逻辑流上：`speech.transcribeStream()` 在 Host 侧返回 `RemoteStream<SpeechSegment, SpeechAudioChunk>`，在浏览器侧返回 `RemoteStreamHandle`，因此 Client 沿上行发送 base64 PCM16 批次，再从同一次调用的下行读取报告。API 逐批校验——必须是规范 base64、整数个 PCM16 采样——并对累计音频施加与完整录音相同的 `maxAudioBytes`/`maxDurationSeconds` 限制。这是协议中全双工流的首个线上用例，而该协议本就是为这类问题预留的。

浏览器使用 AudioWorklet 采集：处理器模块由内联字符串经 Blob URL 加载，`AudioContext` 以 16 kHz 创建，使音频图直接产出识别器要求的采样率；媒体源仍接入既有分析器，波形因此继续可用；一个零增益汇点让处理器被持续驱动而不监听麦克风。每 200 毫秒的批次转换为 Int16，随上行填满即发送；停止时补齐剩余音频、结束上行，并通过与完整录音路径相同的带版本选区插入最终报告。

实时转写渲染在录音行内，并在每份报告到达时替换自身。输入框草稿沿用既有契约：停止时经 `InputActions.insertText()` 一次性插入。

## Alternatives considered

**像参照实现那样在浏览器内识别。** 那样页面会自行签名并直接连接服务，等于把账号密钥放进每个浏览器，并重复一套传输实现。全双工 Remote 让密钥留在 Host，复用客户端已有的认证连接，Web 与桌面客户端共用一份实现。

**用一元调用分块发送音频。** 每次调用都会开启各自的识别器会话，句子无法跨块修正，服务也会丢失让中间报告有价值的上文；把分块结果拼起来，只会把「用户说了什么」变成「模型猜了两次什么」。

**让客户端把每份中间报告直接写入输入框草稿。** 草稿是用户可编辑的缓冲区：在用户打字的同时反复替换其中一段，需要新的编辑操作，还要规定用户自己的编辑落在识别区间内时怎么办。把实时文本显示在录音行内，可以让草稿在停止前的那次插入之前保持不动，而记录结束时用户的注意力也在那里。

**等待本机 SenseVoice 提供方实现流式。** 它是消费完整录音的离线模型；要让它流式，需要另做一套由 VAD 驱动的部分解码设计。按提供方公布 `streaming`，可以让本机识别器保持现有行为，同时云端提供方今天就具备实时能力。

## Consequences

实时录音不再在任一侧缓冲整段语音：音频随采集离开浏览器，并按语速到达识别器，因此文字大致随服务自身的延迟出现，而不是等录音结束再重放。中途取消现在会同时停止采集与识别器会话。

接缝、Remote 与 UI 各自多了一条路径，输入框活动栏多了一个实时文本元素。实时识别仅在提供方公布该能力时可用，因此仍使用本机识别器的部署观察到的行为不变——停止后进入单一「识别中」状态——活动栏也仍需渲染该路径。上行在 JSON 载体上承载 base64，比其编码的 PCM 多出约三分之一字节；批次大小正是在这份开销与延迟之间取平衡。

## Testing

`packages/experimental/speech-to-text/tests/` 覆盖实时接缝（按序报告、未实现该操作的提供方、已撤销的注册、已撤销会话的 signal），`speech-to-text-rtasr/tests/` 覆盖提供方的实时会话（帧重切、音频仍在到达时的报告、字节上限、排空、取消、服务错误），`api-speech-to-text/tests/` 覆盖 Remote（逐批解码与限制、错误映射、取消、在 Remote 调用之外调用），三者均保持逐文件 100% 覆盖率。客户端包覆盖采集（批次边界、尾批补齐、模块 URL 生命周期、处理器错误）与组件（报告渲染、最终插入、取消释放、不支持流式的回退）。演示配置用 Chromium 假音频设备喂入合成的中文句子进行了实测，录音仍在进行时活动栏即显示句子逐渐成形并被修正。
